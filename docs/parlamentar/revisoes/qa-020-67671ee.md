### P2-H: o filtro novo redige menos que o anterior em dois casos de texto entre aspas

- **Código:** `src/leis_mcp/catalog/snapshot.py:57-85`. Um token entre aspas é tratado como uma unidade. `_scrub_token` só age se o texto entre aspas **começa** com `/` ou contém `://`, e remove o userinfo apenas da **primeira** URL do token.
- **Reprodução** (`probe_scrub-67671ee.txt`). Para comparar, rodei a regex do `0c89f78` sobre as mesmas linhas:
  - `error 'fetch https://a.example/x then https://user:SECRET@b.example/y failed' end`: hoje o `SECRET` **permanece**; o `0c89f78` removia `user:SECRET@`.
  - `bad line "GET /index.json?sig=SECRET HTTP/1.1" end`: hoje a query **permanece**; o `0c89f78` cortava em `/index.json`.
- **Esperado:** remover a query e o userinfo de cada URL (ou caminho `/…`) também dentro das aspas, sem perder a linearidade, por exemplo aplicando a mesma lógica aos subtokens separados por espaço dentro das aspas. **Atual:** a redação depende da posição da URL na string.
- **Impacto:** não vi esses formatos nos logs reais (`debug-update-67671ee.log`). Lá, cada URL está sozinha entre aspas ou solta, e é redigida. O caso típico do git, uma única URL entre aspas com token, também é redigido. Por ser uma regressão de cobertura num controle de redação, registro para a revisão de segurança decidir. Para QA não bloqueia.
